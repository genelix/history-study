통섭형 역사 연대표 웹 서비스 개발 세부계획서
1. 프로젝트 개요
1.1 프로젝트명
ChronoScope ― 통섭형 세계사 연대표
부제:
하나의 시간축에서 한국·중국·서양의 정치, 인물, 제도, 종교, 과학, 예술, 기후환경을 동시에 비교하는 역사 탐색 플랫폼
1.2 프로젝트 목적
기존 역사 연대표는 특정 국가 또는 특정 분야 중심으로 구성되는 경우가 많다.
본 프로젝트는 하나의 시간축에 여러 분야의 역사적 사건을 병렬 배치하여 다음 질문에 답할 수 있도록 한다.
* 같은 시대에 한국에서는 무슨 일이 있었는가?
* 중국에서는 어떤 왕조와 제도가 존재했는가?
* 서양에서는 어떤 정치적 변화가 있었는가?
* 같은 시기에 어떤 과학기술이 발전했는가?
* 예술과 문화는 어떻게 변화했는가?
* 종교와 사상은 어떻게 변화했는가?
* 기후변화나 자연환경 변화가 사회에 어떤 영향을 주었는가?
* 서로 다른 지역의 사건 사이에는 어떤 시간적·인과적 관계가 있었는가?
핵심은 역사를 분야별로 분리해서 보여주는 것이 아니라 동일한 시간축에서 서로 비교할 수 있게 하는 것이다.

5. 중요도 등급
역사 데이터는 모든 사건을 동일한 크기로 보여주지 않는다.
A등급 ― Civilization Level
인류 문명의 흐름을 바꾼 사건.
예:
* 로마제국 성립
* 서기 476년 서로마제국 멸망
* 중국 통일
* 산업혁명
* 프랑스혁명
* 신대륙 발견
* 종교개혁
* 제2차 세계대전
* 농업혁명
* 문자 발명
특징:
* 1000년 단위 화면에서 표시
* 가장 크게 표시
* 시간축의 주요 기준점
B등급 ― Regional / Major
한 국가 또는 여러 지역의 역사 흐름을 크게 변화시킨 사건.
예:
* 특정 왕조의 성립
* 중요한 전쟁
* 주요 제도 개혁
* 중요한 종교 전파
* 과학혁명
* 중요한 예술사조
특징:
* 100년 단위 화면에서 표시
* A보다 작게 표시
C등급 ― Detailed
역사를 이해하는 데 유용하지만 전체 문명의 흐름을 바꾸지는 않은 사건.
예:
* 특정 인물
* 특정 발명
* 예술작품
* 지역적 사건
* 세부적인 정치 사건
특징:
* 10년 단위 화면에서 표시
향후 필요하면 D등급까지 확장한다.

6. 시간축 시스템
역사 데이터에서 가장 중요한 부분이다.
6.1 시간 표현
DB에서는 단순 문자열로 연도를 저장하지 않는다.
다음 구조를 사용한다.
year_start
year_end
date_precision
era
예:
year_start: -356
year_end: -323
era: BCE
또는
year_start: 1945
year_end: 1945
era: CE
내부적으로는 BCE를 음수, CE를 양수로 통일한다.
예:
기원전 500년 = -500
기원전 1년 = -1
서기 1년 = 1
서기 500년 = 500
단, 역사적으로 연도 0은 존재하지 않으므로 화면 표시 과정에서 이를 보정한다.

13. 데이터 신뢰도
AI가 역사 데이터를 생성하기 때문에 데이터 신뢰도 관리가 매우 중요하다.
각 데이터에는 다음 필드를 둔다.
confidence
source_count
review_status
ai_generated
human_verified
예:
confidence = HIGH
source_count = 4
review_status = APPROVED
ai_generated = true
human_verified = true
AI가 만든 데이터를 곧바로 서비스에 공개하지 않는다.
권장 workflow:
AI 데이터 생성
      ↓
중복 제거
      ↓
연도/인물/사건 검증
      ↓
출처 확인
      ↓
사람 검토
      ↓
APPROVED
      ↓
Supabase production 데이터

14. AI 데이터 생성 방식
웹 서비스가 매번 인터넷을 검색하지 않는다.
대신 별도의 AI 데이터 제작 과정을 만든다.
역사 지식 + 신뢰할 수 있는 자료
             ↓
        AI 역사 데이터 생성
             ↓
        JSON Schema 검증
             ↓
        중복 검사
             ↓
        역사적 사실 검증
             ↓
        인간 검토
             ↓
        Supabase Import
AI에게 자유로운 서술을 시키지 않고 엄격한 JSON Schema를 출력하도록 한다.

20. Timeline UI 구현 원칙
Timeline은 단순 HTML table이 아니라 시간 좌표 기반의 시각화 컴포넌트로 만든다.
각 이벤트에는:
x = 연도에 따른 위치
width = 이벤트 기간
y = 지역 + 카테고리
를 적용한다.
예를 들어:
year_start = 1800
year_end = 1900
이면 timeline에서 1800~1900 영역을 차지한다.
단일 연도 이벤트는 점 또는 작은 카드로 표시한다.

26. 개발 시 가장 중요한 원칙
원칙 1
UI와 역사 데이터는 분리한다.
역사 데이터가 바뀌어도 UI 코드를 수정할 필요가 없어야 한다.
원칙 2
AI가 생성한 데이터를 코드에 하드코딩하지 않는다.
Supabase가 데이터의 중심이 되어야 한다.
원칙 3
역사 데이터는 version 관리한다.
잘못된 역사 정보가 발견되었을 때 수정 이력을 추적할 수 있어야 한다.
원칙 4
역사적 불확실성을 표현한다.
고대사의 경우 정확한 연도가 알려지지 않은 사건이 많기 때문에:
exact
approximate
range
unknown
등의 정밀도 정보를 관리한다.
원칙 5
A/B/C 중요도는 사실의 가치가 아니라 서비스에서의 표시 우선순위다.
이를 명확하게 정의해야 한다.

27. 최종 목표
이 서비스는 단순한 역사 검색 사이트가 아니라 다음과 같은 서비스를 목표로 한다.
"한 화면에서 같은 시대의 세계를 볼 수 있는 역사 시간 지도"
사용자가 1000년 단위로 문명의 큰 흐름을 보고,
100년 단위로 역사적 구조를 이해하고,
10년 단위로 구체적인 사건과 인물을 탐색할 수 있도록 한다.
궁극적으로는
시간 × 지역 × 분야 × 중요도
라는 4차원 구조로 역사를 탐색하는 것을 목표로 한다.
