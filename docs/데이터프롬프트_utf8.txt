AI Coding Agent용 프로젝트 개발 프롬프트
너는 시니어 풀스택 개발자이자 UI/UX 엔지니어다.
나는 한국사·중국사·서양사를 하나의 시간축에서 비교하고, 정치·인물·제도·종교·과학·예술문화·기후환경을 통합해서 탐색할 수 있는 역사 연대표 웹 서비스를 개발하려고 한다.
프로젝트의 목적은 단순한 역사 검색 사이트가 아니다.
사용자가 동일한 시점에 서로 다른 지역과 분야에서 어떤 일이 일어났는지를 한 화면에서 비교할 수 있는 통섭형 역사 Timeline을 만드는 것이 목표다.

1. 기술 환경
다음 기술을 기본으로 사용한다.
* Frontend: Next.js + TypeScript
* UI: Tailwind CSS
* Component: shadcn/ui
* Database: Supabase PostgreSQL
* Source control: GitHub
* Deployment: Netlify
필요한 경우 추가 라이브러리를 사용할 수 있지만, 반드시 추가 이유를 설명한다.

3. 중요도
모든 역사 이벤트에는 중요도가 있다.
A
B
C
의미:
A = 문명사적/세계사적 핵심 사건
B = 국가 또는 지역사의 중요한 사건
C = 세부적인 역사 정보
중요도는 UI 표시 우선순위이지 역사적 가치에 대한 절대적인 평가가 아니다.

4. Timeline 요구사항
Timeline은 다음 3가지 모드를 지원해야 한다.
1000년
100년
10년
1000년 모드
A등급만 표시한다.
100년 모드
A+B 표시
10년 모드
A+B+C 표시
단, 사용자가 필터를 조정할 수 있도록 구현한다.

5. Timeline 데이터
이벤트는 최소한 다음 속성을 가져야 한다.
interface HistoricalEvent {
  id: string;
  title: string;
  yearStart: number;
  yearEnd: number;
  region: string;
  category: string;
  importance: "A" | "B" | "C";
  summary: string;
  historicalSignificance?: string;
  cause?: string;
  consequence?: string;
}
실제 DB 구조에서는 확장 가능성을 고려한다.

6. 연도 처리
BCE와 CE를 모두 지원해야 한다.
내부적인 시간 계산에서는:
BCE 500 = -500
BCE 1 = -1
CE 1 = 1
CE 500 = 500
방식을 사용한다.
단, 역사적으로 year 0이 존재하지 않는다는 점을 고려하여 화면에 표시할 때 정확하게 변환한다.
또한 다음과 같은 역사 데이터의 불확실성을 지원한다.
exact
approximate
range
unknown
예:
yearStart = -2500
yearEnd = -2400
precision = "approximate"

9. Timeline 구현
Timeline은 연도 데이터를 화면 좌표로 변환하는 별도의 로직을 만든다.
예:
yearToPosition(year, timelineStart, timelineEnd)
기간이 있는 이벤트는:
left = yearStart 위치
right = yearEnd 위치
로 계산한다.
단일 연도 이벤트는 점 또는 카드 형태로 표시한다.
Timeline rendering logic은 UI 컴포넌트와 분리한다.

10. Supabase
Supabase PostgreSQL을 프로젝트의 핵심 데이터 저장소로 사용한다.
최소한 다음 테이블을 설계한다.
events
people
event_people
event_relations
sources
regions
event_categories
필요하면 추가 테이블을 제안한다.
DB migration 파일을 생성하고 GitHub에서 관리한다.

11. 역사 데이터
역사 데이터는 웹서비스 실행 시 실시간 검색하지 않는다.
역사 데이터는 별도의 AI 데이터 생성 과정에서 만든 JSON을 Supabase에 import한다.
따라서 application code와 역사 데이터를 철저히 분리한다.
예:
data/
  schema/
  seed/
  import/

12. 데이터 검증
AI가 만든 JSON을 바로 DB에 넣지 않는다.
다음 검증 프로그램을 만든다.
JSON
 ↓
Schema Validation
 ↓
Required Field Validation
 ↓
Year Validation
 ↓
Category Validation
 ↓
Importance Validation
 ↓
Duplicate Detection
 ↓
Import
잘못된 데이터가 있으면 어떤 record가 왜 실패했는지 출력한다.

16. 성능
처음부터 모든 역사 데이터를 한 번에 렌더링하지 않는다.
다음 방법을 사용한다.
현재 Timeline 범위
        ↓
해당 범위 데이터만 조회
        ↓
필터 적용
        ↓
렌더링
Supabase query에 적절한 index를 생성한다.
특히 다음 필드를 고려한다.
year_start
year_end
region
category
importance

17. 데이터 API

가능하면 다음과 같이 repository/service 계층을 만든다.

  historical-events/

19. 반드시 지켜야 할 개발 원칙
원칙 1
하드코딩된 역사 데이터를 React component에 넣지 않는다.
원칙 2
Timeline logic과 UI를 분리한다.
원칙 3
DB schema와 TypeScript type을 일치시킨다.
원칙 4
역사 데이터와 애플리케이션 코드를 분리한다.
원칙 5
모든 중요한 기능에 TypeScript type을 적용한다.
원칙 6
향후 데이터가 10만 건 이상으로 증가할 수 있다는 가정으로 설계한다.
원칙 7
사용자가 현재 보고 있는 시간 범위 밖의 데이터를 불필요하게 렌더링하지 않는다.
원칙 8
A/B/C 중요도는 Timeline 시각적 계층 구조에 반영한다.
